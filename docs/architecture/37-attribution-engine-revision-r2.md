## 3. Frongello Protection Design

To prevent the path-dependent compounding factor $\prod_{j=1}^{t-1} (1 + R_{b,j})$ from collapsing to zero during worthless option expirations or absolute asset liquidations ($R_{b,j} = -100\%$), we enforce a compounding safety floor:

### A. Mathematical Safety Floor
The daily return series used in the compounding equation is forced to a lower bound:
$$R'_{b,t} = \max(R_{b,t}, -0.999999)$$
$$R'_{p,t} = \max(R_{p,t}, -0.999999)$$
* **Liquidation Handling**: A complete loss of $-100\%$ is scaled to $-99.9999\%$ in the compounding loop. The remaining $0.0001\%$ residual is captured in the ledger as a `liquidation_tracking_residual` value.
* **Extinction Handling**: If the benchmark index is discontinued, the calculation is marked as `FAILED`. A new session must be staged with a replacement benchmark reference URN starting from the discontinuation date.
* **Audit & Replay**: These bounds are applied inside the stateless `CompoundingCalculator`, ensuring identical inputs always yield identical outputs.

## 4. Canonical Manifest Design

To guarantee that the input manifest hash is independent of whitespace, formatting, or serialization quirks, the engine implements the `CanonicalManifestSerializer` specification:

```
[Input Data Dict]
   -> 1. Remove Null Keys
   -> 2. Sort Keys Lexicographically
   -> 3. Format Decimals to Strings with 12 Decimal Places
   -> 4. Format Timestamps to UTC ISO-8601 (YYYY-MM-DDTHH:MM:SS.000000Z)
   -> 5. Sort Arrays by Unique URN/ID fields
   -> 6. Serialize to UTF-8 Bytes
   -> 7. Compute SHA-256 Hash
```

* **Numeric Standardization**: All float and decimal values are normalized to a string with a fixed precision of 12 decimal places (e.g. `0.100000000000`).
* **Array Ordering**: Arrays of holdings are sorted alphabetically by `asset_urn`; execution fills are sorted by `execution_id`.

## 5. Benchmark Service Boundary

The Attribution Engine does not calculate benchmark returns or manage constituent weights. It treats benchmarks as read-only external references.

* **Benchmark Service Boundary**: Lives under the Portfolio/Market Data context. It owns index price feeds, component rebalancing, and daily index return calculations.
* **Attribution References**:
  - `benchmark_reference_urn`: Foreign URN identifier of the benchmark (e.g., `urn:benchmark:sp500`).
  - `benchmark_snapshot_reference`: Foreign reference to a frozen daily return series generated by the Benchmark Service for the session window (e.g., `urn:benchmark:snapshot:sp500:2026-q1`).

### BenchmarkSnapshot Contract:

{

}

## 6. Version Invalidation Design

When a retrospective correction recalculates historical data:
1. The engine inserts new `PerformanceAttributionRecord` entries with `attribution_version = previous_version + 1` and `is_active = True`.
2. The engine updates the old versions to `is_active = False` in the same database transaction.
3. Upon commit, the engine publishes the version invalidation events:
   - `AttributionVersionSupersededEvent` (v1) - contains single record version mapping.
   - `TransactionVersionSupersededEvent` (v1) - contains session-level URN mapping.
4. Downstream consumers (Performance Engine, Capital Allocation) maintain a local lineage graph. When a supersede event is received, they traverse the lineage to invalidate their local caches and trigger scoring updates.

## 7. Recomputation Protection Design

To prevent cascading event storms during deep historical recalculations:
* **Sequential Throttling**: Batch recalculations are processed chronologically in batches of at most 4 concurrent sessions.
* **Idempotency Strategy**: The engine checks the unique `recalculation_request_id` against a deduplication cache (`recomputation_idempotency_ledger`) to drop redundant requests.
* **Superseding Chain Limits**: A maximum record version ceiling of 99 is enforced. If version updates exceed 10, the calculation halts and triggers an alert for data feedback loops.
* **Propagation Limits**: Event propagation is capped at 3 hops downstream (Attribution $\to$ Performance $\to$ Capital Allocation).

## 8. Replayability Verification
The combination of the `raw_input_manifest_hash` (generated via the canonical serializer) and the stored `compounding_strategy` name guarantees complete replayability. Any price, constituent, or holdings adjustment will cause a mismatch against the canonical hash, flagging data drift instantly.

## 11. Acceptance Criteria
1. The compounding engine must cap benchmark and portfolio daily returns at a minimum of $-99.9999\%$ in Frongello calculations.
2. The `AttributionSession` must record the active `compounding_strategy` name.
3. The manifest serializer must deterministically sort and normalize JSON inputs.
4. Database updates to mark superseded records as inactive must execute in the same transaction as the new record inserts.
