# ADR-032: Performance Evaluation and Confidence Calibration Model

## Status
Approved

## Date
2026-06-14

## Context
Karsa’s system deploys automated workers, trading strategies, and LLM providers across multiple portfolios. To optimize allocation and select the best models, we must evaluate their performance.

This requires solving several key challenges:
1. **Calibration**: Current confidence scores generated by LLM workers are highly unreliable and uncalibrated (often overconfident). We need a model that uses historical predictions and actual outcomes to produce calibrated confidence.
2. **Replayability & Recalculation**: If metric calculation formulas are updated, we must be able to backtest the new formulas against historical traces. However, we must also preserve the exact evaluation state seen by the platform at any past decision timestamp.
3. **Outcome Linkage**: We must cleanly map decisions, thesis versions, and worker executions to their actual outcomes and resulting evaluations without creating database cross-locks.
4. **Isolating Quality**: A correct investment thesis can lead to an unprofitable trade due to bad execution (high slippage) or poor portfolio sizing. We must separate these dimensions.

## Decision
We implement the following Performance Evaluation Model:

1. **DecisionEvaluation as Primary Aggregate Root**:
   - The **`DecisionEvaluation`** aggregate is the primary unit of learning in Karsa. It maps a single `decision_id` to its realized execution outcome.
   - `PerformanceEvaluation` (the subject-level scorecard) is demoted to a **read-side projection** dynamically compiled from the history of discrete `DecisionEvaluation` records.
2. **Isolating Performance Dimensions**:
   - Each `DecisionEvaluation` partitions its metrics into three distinct value object dimensions:
     - **Thesis Quality**: Evaluated against invalidation parameters (Brier score, parameter deviations).
     - **Execution Quality**: Evaluated against execution performance (slippage, fill latency, token usage).
     - **Allocation Quality**: Evaluated against capital sizing metrics (Sharpe ratio, drawdowns, excess returns).
3. **ExecutionOutcome Shared Contract**:
   - `ExecutionOutcome` is defined as a **Shared Integration Event Contract** in the shared domain. It is produced by execution/observability blocks and consumed by both Performance (to evaluate decisions) and Attribution (to calculate costs). It contains raw realized facts (returns, fills, latencies) and is immutable.
4. **Regime-Conditioned Calibration**:
   - Calibration metrics and bins are stored partitioned by `regime_id` keys. A worker's raw confidence is translated into calibrated probabilities conditioned on the active market regime (e.g. Bull, Bear).
5. **ACTIVE + CANARY Evaluation Strategy**:
   - We enforce the **ACTIVE + CANARY** policy for concurrent active versions.
   - The `ACTIVE` version and `CANARY` version run under **separate execution bindings**, and are evaluated under **separate scorecards** and **separate calibration tables**. This allows direct performance comparisons.
6. **Hybrid Persistence Model**:
   - **`EvaluationSnapshot`** is **immutable forever** (soft-deletes only, never edited). It records the exact performance values used by the platform at a specific timestamp.
   - **`DecisionEvaluation`** (the active aggregate state) and its projections are **recomputable**. Rebuild workers can scan outcome histories to regenerate projections if metric calculation formulas evolve.

## Consequences
- **Absolute Traceability**: Every evaluation maps back to a discrete decision, preventing state pollution.
- **Trustworthy Predictions**: Downstream risk PDP/PEP blocks utilize statistically calibrated scores instead of raw worker confidence.
- **Isolating Blame**: Risk officers can determine if a loss was caused by a flawed thesis, poor execution, or bad capital sizing.
- **Canary Promotion Safety**: Canary versions are calibrated separately, enabling data-backed promotion workflows.
